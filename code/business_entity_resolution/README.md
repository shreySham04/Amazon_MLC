# Business Entity Resolution — End-to-End ML Pipeline

## Quick Start (TL;DR)

```bash
# 1. Install dependencies
pip install -r requirements.txt

# 2. Train the model (runs blocking + feature engineering + LightGBM)
cd student_resource
python code/business_entity_resolution/src/train.py

# 3. Generate predictions for the test set
python code/business_entity_resolution/src/predict.py

# 4. Validate the output
python utils/validate_submission.py \
    --matching output/matching_results.tsv \
    --candidate output/candidate_pairs.tsv \
    --test-dir dataset/test
```

## Pipeline Description

### Stage 1 — Normalisation (`normalize.py`)

Applied to every name and address in all three sources:

| Operation | Detail |
|-----------|--------|
| Unicode NFKD | Decompose + strip combining marks (handles French accents, transliterations) |
| Legal suffix canonicalisation | Corp→corp, Pvt Ltd→pvt ltd, SARL→sarl, GmbH→gmbh, etc. |
| Abbreviation expansion | Rd→road, St→street, Ave→avenue, Bd→boulevard (French), Ph→phase (India) |
| `&` / `+` → `and` | Normalise conjunctions |
| Core name | Name with legal suffixes + stopwords removed |
| Sorted-token name | Bag-of-words, order-invariant representation |
| Acronym | Initialism from core tokens |
| Postal code extraction | Regex-extracted 5–6 digit PIN/ZIP |
| Street number extraction | Leading numeric components |

### Stage 2 — Blocking (`blocking.py`)

Five complementary blockers run per country partition (union of results):

| Blocker | Recall contribution |
|---------|---------------------|
| Postal code | Exact PIN/ZIP match |
| Rare token | Share a high-IDF name token (DF ≤ 1% of corpus) |
| TF-IDF char-3gram | Sparse cosine top-30 neighbours per S1 entity |
| Embedding ANN | FAISS top-25, `paraphrase-multilingual-MiniLM-L12-v2` |
| City token | Last 2 significant address tokens match |

Target: ≥ 97% pair completeness with manageable candidate volume.

### Stage 3 — Feature Engineering (`features.py`)

40+ features per candidate pair:

**Name features**
- Jaccard on tokens and char 3/4-grams
- Levenshtein / Jaro-Winkler / partial ratio / token-sort / token-set ratio (RapidFuzz)
- Core-name exact match, sorted-token exact match, acronym match
- Legal suffix agreement

**Address features**
- Edit distance, token overlap (Jaccard), partial ratio, token-set ratio
- Postal code: exact / prefix / both-missing
- Street number match
- Landmark presence flag

**Semantic features**
- Cosine similarity of multilingual embeddings (name + address concatenated)

**Context features**
- Candidate rank within S1 group (by embedding cosine)
- Score gap to best candidate
- Number of candidates per S1 entity

**Meta**
- Missing-field indicators, source (S2 vs S3)

### Stage 4 — Matching Model (`train.py`)

- **Model**: LightGBM binary classifier
- **Positives**: ground-truth matched pairs
- **Negatives**: hard negatives from blocking candidates (not in GT)
- **Ratio**: up to 10× hard negatives per positive per S1 entity
- **Split**: GroupShuffleSplit by S1 entity (no leakage)
- **Calibration**: LightGBM `predict_proba` (built-in Platt-like)
- **Threshold tuning**: grid search over [0.20, 0.95] optimising macro F0.5 on validation

### Stage 5 — Decision + Post-processing (`predict.py`)

1. Apply tuned threshold per candidate (conservative; precision > recall due to F0.5 metric)
2. Output empty list for S1 entities with no candidates above threshold (singleton prediction)
3. Conflict resolution: if one S2/S3 record is claimed by multiple S1 entities, assign it only to the highest-scoring one

## Runtime & Resource Estimates

| Stage | Approx. time (24 GB RAM) | Notes |
|-------|--------------------------|-------|
| Normalise train | 15–30 min | ~12.5M records total |
| Blocking (train) | 1–2 h | Embeddings cached after first run |
| Features (train) | 30–60 min | Cached as Parquet |
| LightGBM training | 10–30 min | 1000 trees, early stopping |
| Predict (test) | 1–2 h | Same stages, smaller S1 |

Intermediate artefacts are cached in `src/../models/` so re-runs skip completed stages.
